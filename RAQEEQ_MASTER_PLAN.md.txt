# 1. PROJECT IDENTITY

**Project name:** RAQEEB  
**Arabic name:** رقيب  
**Product category:** AI-powered Digital Trust Investigation Platform  
**Target audience:** UAE-focused users  
**Initial language:** English only  
**Product format:** Web application  
**Future possibility:** Browser extension using the same investigation engine.

RAQEEB is being developed as a hackathon MVP.

We are not planning to publish it commercially or launch it publicly at this stage.

Our priorities are:

1. Strong investigation capabilities.
2. Evidence-based organization verification.
3. Explainable risk scoring.
4. Working URL, message, and screenshot investigations.
5. Excellent UI/UX.
6. Privacy-conscious processing.
7. A convincing live hackathon demonstration.

### Core concept

RAQEEB is not just another AI chatbot that tells users whether a message is suspicious.

It is an investigation platform that collects evidence, verifies claims, analyzes technical indicators, checks available threat intelligence, and generates structured investigation reports.

### Main differentiator

**"Verify the Claim, Not Just the Link."**

Example:

A user receives a message claiming to come from a UAE bank.

RAQEEB should investigate:

- Which organization does the message claim to represent?
- Does the submitted domain belong to that organization?
- Is the domain similar to a legitimate domain?
- Are there suspicious technical indicators?
- Are there known threat intelligence findings?
- Does the message contain suspicious requests or manipulation techniques?
- Can the organization's identity be independently verified?

The system should explain its conclusions using collected evidence.

# 5. INVESTIGATION ENGINE

Build a shared investigation pipeline.

Proposed workflow:

1. Receive user input.
2. Validate and process the input.
3. Extract relevant text and information.
4. Extract URLs and domains.
5. Identify claimed organizations.
6. Identify payment requests and suspicious claims.
7. Perform technical analysis.
8. Check threat intelligence sources.
9. Verify organization identity.
10. Correlate collected evidence.
11. Use AI to interpret and explain the evidence.
12. Calculate the risk score using deterministic logic.
13. Generate a structured report.

Distinguish between:

- Confirmed malicious evidence.
- Suspicious indicators.
- Verified information.
- Unverified claims.
- Contradictory findings.
- Missing information.

Never invent findings, sources, or verification results.

If the evidence is insufficient, return Unknown Risk.

# 6. ORGANIZATION IDENTITY VERIFICATION

This is one of our most important differentiators.

Design a reliable and practical verification system.

### A. Trusted organization registry

Build a curated registry of important UAE organizations.

Include manageable initial coverage of:

- Banks.
- Government organizations.
- Delivery companies.
- Telecommunications providers.
- Payment services.

Each organization entry should include, where available:

- Organization name.
- Official domain.
- Official website.
- Organization category.
- Trusted source reference.
- Verification status.
- Known official subdomains or additional domains.

### B. Authoritative verification

Prioritize:

1. Organization's official website.
2. Official UAE government directories and portals.
3. Official regulator and authority websites.
4. Other trustworthy primary sources.

Starting references:

https://u.ae/

https://designsystem.gov.ae/

Do not treat an LLM answer, search result, or social media account as sufficient proof of official identity.

### C. Domain comparison

Check:

- Exact official domain matches.
- Suspiciously similar domains.
- Misspellings.
- Lookalike characters.
- Unexpected subdomains.
- Unrelated domains claiming to represent organizations.
- Redirect destinations.

Understand the difference between a genuine subdomain and a domain that merely contains an organization's name.

### D. Technical checks

Evaluate:

- Domain registration information where available.
- Domain age where reliable.
- HTTPS and TLS information.
- DNS records.
- Redirect chains.
- URL structure.
- Suspicious URL patterns.

These are supporting indicators, not standalone proof.

HTTPS does not prove legitimacy.

A new domain does not automatically prove fraud.

### E. Verification outcomes

Use these outcomes:

- Verified Match.
- Possible Impersonation.
- No Verified Relationship Found.
- Unable to Verify.

Explain the evidence supporting each result.

### F. Recommendation

Prefer a curated organization registry combined with deterministic domain comparison and authoritative source references.

Do not claim an organization has been verified without reliable supporting evidence.

# 8. RISK SCORING ENGINE

Use a transparent weighted scoring system.

The score is a risk assessment, not a statistically validated probability of fraud.

Proposed weights:

| Category | Weight |
|---|---:|
| Threat intelligence findings | 30% |
| Organization identity verification | 25% |
| URL and domain technical analysis | 20% |
| Message content and manipulation indicators | 15% |
| Contextual indicators | 10% |
| Total | 100% |

You may recommend changes after analyzing the technical implications.

Each category should produce a normalized contribution.

The final score should be calculated by deterministic logic.

### Risk categories

| Score | Category |
|---|---|
| 0–24 | Low Risk |
| 25–49 | Moderate Risk |
| 50–100 | High Risk |
| Insufficient reliable evidence | Unknown Risk |

The system must support Unknown Risk.

### Scoring rules

- Confirmed malicious intelligence findings should have a strong impact.
- Verified official domains should reduce identity-related risk, but not automatically make a message safe.
- Suspicious domain mismatches should increase risk.
- Suspicious message language alone should not prove fraud.
- Missing information must not count as evidence of safety.
- API failures must not count as clean results.
- Contradictory evidence should be handled explicitly.

Show users a breakdown of category contributions and explain why each score was assigned.

Keep the weights configurable.

Do not promise 100% safety.
